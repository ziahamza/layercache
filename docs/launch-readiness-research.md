# LayerCache launch-readiness research — 2026-09-26

This note assesses the first useful product promised in the current handoff: a CLI-connected, self-serve Team Cache with a team dashboard. It distinguishes tested code from a publicly usable service. Evidence comes from repository source and QA, GitHub's first-party repository state checked on 2026-09-26, and official GitHub/Turborepo documentation. Recommendations below are inferences from that evidence.

## First-use path and current evidence

1. **Install a trusted CLI.** `layercache connect` and `action/setup` exist, but the [verified installer](../scripts/README.md#L1-L28) requires an immutable published release and [runner setup](../action/setup/README.md#L1-L37) still shows `OWNER/layercache`, `v0.1.0`, and a full commit placeholder. The [GitHub release list](https://github.com/ziahamza/layercache/releases) was empty when checked on 2026-09-26 (`gh release list` returned `[]`). A build from source works for a pilot; it is not the advertised download/install path.
2. **Sign in and make a project.** The [hosted flow](self-serve-cloud.md#L5-L19) implements GitHub sign-in, team creation, repository-backed project creation, invitations, and `connect --cloud ... --github-cli`; project creation checks GitHub repository administrator permission ([source](../internal/portal/portal.go#L426-L465)). The sample [cloud configuration](../deploy/cloud/config.example.json) still contains a placeholder hostname/client ID. The [operator guide](self-serve-cloud.md#L33-L63) requires a separate OAuth app, protected secrets, bounded filesystem, TLS proxy, and real post-deploy checks. Repository code/CI alone do not show that a public instance has been deployed.
3. **Connect and run.** `connect` discovers authorized projects, exchanges the GitHub credential, creates a protected project config and isolated Local Cache, and prints commands to start the daemon and open the dashboard ([source](../internal/cli/cloud_connect.go#L75-L239)). Connection does not start the daemon or modify the build workflow ([guide](self-serve-cloud.md#L15-L19)). For Turbo use, the engineer must invoke `layercache run` with that config; the [existing rollout](rollout-2026-09-22.md#L20-L24) explicitly warns that plain `pnpm` does not route through LayerCache. A cold upload followed by a fresh checkout/runner restore is the first meaningful success, beyond a page view or connected status.
4. **Observe and share.** The [dashboard](../internal/portal/assets/index.html) shows storage, artifacts, hits/misses, members, roles, invitations and a copyable CLI command; the [cloud QA](../qa/cloud/RESULTS.md#L3-L30) passed browser flows in Chromium/Firefox/WebKit plus durable store/authorization tests. The browser test uploads an artifact directly through the API after connecting a fake `gh` credential ([test](../qa/cloud/browser.ts#L24-L25)); it does not establish a real GitHub OAuth round trip, a public HTTPS deployment, a Turbo cold/warm job on the new service, or production network/storage behavior. QA states those limits explicitly ([results](../qa/cloud/RESULTS.md#L29-L31)). The older operator-managed cache *does* have fresh-worktree and hosted Parle reuse evidence, including 49/49 Team Cache hits; those results are from the previous gateway and are not self-serve tenant acceptance ([rollout](rollout-2026-09-22.md#L42-L84)).

## Ranked gates

### Launch-critical for a limited cache beta

1. **Make distribution and scope agree.** As of this check, no release exists. At the merged `68a8d0d` baseline, the [release workflow](https://github.com/ziahamza/layercache/blob/68a8d0d698e0acced54712955a6822c4aa98dd62/.github/workflows/release.yml#L17-L65) requires a successful, exact-commit Linux arm64 KVM *Public Build* qualification on a protected main branch, and the [publish job](https://github.com/ziahamza/layercache/blob/68a8d0d698e0acced54712955a6822c4aa98dd62/.github/workflows/release.yml#L745-L747) depends on that gate. The [native workflow](../.github/workflows/public-build-native.yml#L17-L19) needs a specifically labeled self-hosted arm64 runner; its [GitHub runs page](https://github.com/ziahamza/layercache/actions/workflows/public-build-native.yml) had no runs when checked. Yet the self-serve cache slice explicitly excludes Public Builds ([boundary](self-serve-cloud.md#L65-L69)). **Inference:** release a clearly scoped Team Cache binary through the existing native cache/protocol/performance gates, or supply the arm64 KVM evidence; keep Public Build capability disabled/unadvertised until its own gate passes. Do not call a source checkout an installable release.
2. **Deploy one isolated real instance and prove the complete path.** Provision a distinct hostname, OAuth app, TLS route, physically bounded pool, key/secret files, backup, restart, and an external health check, then run a real administrator and invited member through sign-in, project creation, CLI connect, Turbo cold upload, and fresh-runner restore. Verify reader/writer revocation and operator recovery on that instance. The [operator runbook](self-serve-cloud.md#L33-L63) names these prerequisites; [cloud QA](../qa/cloud/RESULTS.md#L29-L31) says they remain unproven. Keep the deployed version pinned and record a rollback point. A working hosted service and one external engineer's successful restore are the beta exit criteria.
3. **Limit public signup to available capacity and publish a clear offer.** The service permits any GitHub user to create up to five teams and uses global 128-team/128-project limits ([store](../internal/portal/store.go#L150-L168), [project capacity](../internal/portal/store.go#L235-L266)); [the guide](self-serve-cloud.md#L61-L69) says billing, deletion, and automated quota purchase are absent. The physical pool prevents unbounded writes but a stranger can consume scarce capacity or a project slot. **Inference:** start with an explicit, operator-controlled free beta/allowlist and documented per-project limits/support channel, then add deletion/lifecycle and capacity visibility before unrestricted signup or paid launch. Pricing and payment collection are unnecessary for a small invited beta, but an unrestricted “self-serve cloud” claim needs an answer to capacity exhaustion and account exit.
4. **Reduce GitHub authorization friction before wider adoption.** The browser OAuth flow asks for `read:user repo` ([guide](self-serve-cloud.md#L33-L37)); GitHub says `repo` grants broad access to public/private repositories and that [GitHub Apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps) allow specific repositories, fine-grained permissions, short-lived tokens, and scalable limits. **Inference:** OAuth is workable for trusted design partners, but a repository-scoped GitHub App should be the next auth milestone before a broad organization rollout. The UI should also make the admin-permission requirement and why it exists apparent before the consent/install step. Invites currently appear only after the recipient signs in; [no notification is sent](self-serve-cloud.md#L17-L17), so a team admin must separately share the link.

### Next, after the first pilot has repeat usage

5. **Make CI onboarding a product flow.** Add a generated, version-pinned workflow snippet for an authorized project, including the actual cloud endpoint and OIDC permissions, and validate it with one trusted main-branch job. Today [runner setup](../action/setup/README.md#L8-L54) is a template with placeholders and separate action steps, and [deployment guidance](deployment.md#L17-L23) requires hand migration. The current CLI dashboard copy command only connects a developer machine. The measurable target is a first remote hit from a fresh GitHub-hosted runner, with clear cache miss diagnostics.
6. **Prove differentiated value against existing free caches.** [GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching) includes a default 10 GB/repository cache and retention controls; [Turborepo](https://turborepo.dev/docs/core-concepts/remote-caching) documents free Vercel Remote Cache and self-hosted API compatibility. **Inference:** a generic “cloud cache” is not a sufficient paid proposition. Pilot evidence should compare repeat build time, cross-worktree/CI reuse, storage/transfer, and cache hit provenance for representative real projects; do not turn the synthetic [performance gate](performance.md#L21-L31) into a fleet-wide savings claim. The existing [Parle field result](rollout-2026-09-22.md#L76-L84) is promising but specifically excludes CPU-savings claims.
7. **Add machine enrollment only when it improves support or policy.** A config and daemon PID do not form a revocable machine identity. The [dashboard roadmap](dashboard.md#L74-L90) correctly puts enrolled identity, heartbeat/stale state, then policy management ahead of runner orchestration. Implement only the minimal machine status needed to troubleshoot cache adoption, after the service has active users.
8. **Keep hosted runners as a separate later product.** Existing workflows already run on GitHub-hosted runners; the first slice shares artifacts without owning compute. A private runner fleet needs registration, isolation, job leases, cancellation, cleanup, utilization and cost accounting; [GitHub's runner guidance](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners) makes the host responsible for OS/software upkeep, and [GitHub's secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use) warns that persistent runners can be compromised by workflow code. **Inference:** launching runners before proving cache adoption adds a much larger trust/operations surface without closing the current first-use gap. Public Builds have a distinct publication contract ([domain model](../CONTEXT.md#L23-L29)); do not rename them “cloud runners.”

## Product position and prioritized roadmap

Launch claim for the first beta: **“Connect an existing CLI and GitHub Actions job to a shared, project-isolated cache; see what was stored and reused.”** This matches the implemented team/project/auth model and the current support boundaries. Success requires a real release, live service, an external team's cold/warm restore, and honest before/after reports. Machine management and hosted runners should be visible as future directions, not required to make the cache beta usable. Phone and Parle are valuable pilot workloads; their existing operator-managed services and native signing flows should remain stable while a separate test project validates the new self-serve service. The older Phone review status and Parle Safari acceptance are project rollout details, not global prerequisites for a Team Cache beta ([rollout](rollout-2026-09-22.md#L92-L107), [native rollout](native-cache-rollout.md#L3-L8)).
